# Exercise 4: Fix the Robot!

Welcome to the Fix the Robot exercise. Your team has inherited legacy kinematics code controlling an experimental robotic arm joint. The code is unoptimized, fragile, and lacks type safety. You have exactly **60 minutes** to clean it up using modern software engineering metrics and design patterns.

---

## Project structure & Evaluation Criteria
*This lab utilizes automated Git history analysis and non-standard architecture constraints to ensure authentic human development.*

1. **Mandatory Git Atomic Commits**: You are strictly graded on your development history. You must submit exactly **4 sequential commits** on your branch. Each commit must contain *only* the code lines associated with that single refactoring task.
2. **Arbitrary Variable Naming Rule**: To override generic LLM assumptions, all global constants extracted during the lab **MUST** begin with the precise identifier prefix: `ROBO_SYS_` (e.g., `ROBO_SYS_GRAVITY`). Generic or standard names generated by an AI will result in an immediate automatic zero.
3. **Method Extraction Enforcements**: When breaking up the monolithic calculation function, you are strictly required to create exactly three distinct helper functions. They must be named precisely:
   * `_stage_one_kinematics` (Processes baseline joint metrics)
   * `_stage_two_signal_overrides` (Handles emergency/safety logic)
   * `_stage_three_power_profile` (Handles battery and voltage adjustments)

## Your Tasks (10 points)

### Task 1: Baseline Kinematics Assessment (15 Mins)
Analyze and document the initial operational metrics of `script.py`:
```bash
# Check Cyclomatic Complexity of the firmware calculation engine
radon cc script.py -s

# Scan for PEP 8 formatting errors and structural smells
flake8 script.py

# Confirm that the baseline safety tests are green
python -m unittest test_script.py
```

Note: if you have error during running radon  or flake, try to prepend command with `python -m`
```bash
python -m flake8 script.py
```

### Task 2: Executing Clean Firmware Refactoring (25 Mins)
Refactor `script.py` into production-ready firmware while preserving physical logic. You must process your changes in **4 distinct, atomic Git commits**:

*   **Commit 1**: Extract all magic numbers into `ROBO_SYS_` prefixed uppercase global constants.
*   **Commit 2**: Isolate the deep `if/else` logic trees into the three mandatory helper functions (`_stage_one_kinematics`, `_stage_two_signal_overrides`, `_stage_three_power_profile`).
*   **Commit 3**: Eradicate code duplication between `calculate_actuator_torque` and `log_telemetry` by chaining your new helper engine.
*   **Commit 4**: Add strict Python type hints to all function signatures (e.g., `def _stage_one_kinematics(joint_type: str, payload_kg: float) -> float:`).

*Run your unit tests after every single step to confirm your safety net is intact.*

## EXTRA Task (+5 Points)
**Objective: Identify a critical firmware safety vulnerability.**

In the legacy code, the `EMERGENCY_BRAKE` mechanism contains a dangerous logical race condition caused by deep indentation nesting. Under specific system states, the firmware will accidentally apply a power boost *after* the brake zeroes out the torque.

To earn your extra 5 points:
1. Write a new unit test in `test_script.py` called `test_emergency_brake_safety_violation` that captures this specific failure mode.
2. Ensure your refactored helper functions decouple the safety overrides from the power profile logic completely, ensuring that if an `EMERGENCY_BRAKE` signal is present, final torque is unconditionally locked at `0.0` regardless of battery level.
